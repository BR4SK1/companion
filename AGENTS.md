# Repository working guardrails

This repository contains architecture documentation, shared-library code ([`libraries/openrouter`](libraries/openrouter/README.md) — transport plus typed Decisions and Chat contracts; [`libraries/postgres`](libraries/postgres/README.md) — connection lifecycle, transactions, and a migration runner over `pg`), an implemented worker slice in [`apps/worker`](apps/worker/README.md) — durable grouped conversation work on PostgreSQL with OpenRouter response-pattern decisions preceding chat generation, plus a private bearer-token HTTP ingest/read API — and the authenticated web client with its BFF edge in [`apps/web`](apps/web/README.md) — owner-only Keycloak OIDC sign-in, signed-cookie sessions, and authenticated routes that call the worker's private API with a shared service-to-service credential. Owner authorization happens only at the BFF; identity-provider subjects never enter domain records or worker calls. Application containers and a K3s application Helm chart exist under [`deploy`](deploy/README.md), with environment-specific values and secret delivery kept in local-only files outside version control; there is still no deployment controller or trigger, and a merge does not deploy. That describes the current state, not a permanent implementation ban. Do not infer authorization for future implementation from documented designs or scaffold contents: proceed only within the scope explicitly authorized for the current task. Keep unresolved choices explicit and update relevant documentation when a decision is actually made.

## Boundaries

- All future application containers target K3s. PostgreSQL and Keycloak are existing services external to K3s; never add them as chart dependencies or provision them here.
- Keep the product owner-only: authorize the owner at the web BFF, separately from domain identity. Do not introduce tenant abstractions or cascade identity-provider/user IDs through domain records and work.
- Preserve a single continuous visible thread. Internal sequential segments may support processing/history without fragmenting the UI.
- Domain types, schemas, and queries belong to their owning domain. Shared infrastructure libraries expose integration boundaries; do not create a generic shared-types library.
- Keep shared OpenRouter transport separate from typed chat and decision adapters. Decisions use OpenRouter's native typed question/answer variants — `choice`, `noul`, and `score` — preserved as returned: optional native probability distributions on choice and score answers, and a noul probability that stays a number rather than being coerced to a Boolean (see [`libraries/openrouter/README.md`](libraries/openrouter/README.md)). Shared libraries define transport and capability contracts, not deployment-specific policy or rule content.
- Use relational PostgreSQL as the data model; do not add a document-compatibility layer. Durable grouped messaging is a requirement, but queue technology and detailed turn/retry policy remain open.
- New implementations that produce traceable decisions or events should use typed relational owned data and trace correlation, following the established feature-owned attempt-tracing pattern (see [`apps/worker/README.md`](apps/worker/README.md) for the reference implementation) — no generic JSONB payloads, document facades, or EAV. This does not impose a requirement to trace every internal action. Domain ownership is preserved: domain data stays with its owning domain, rather than being mandated into worker storage for non-worker domains. Any exception to the established pattern must be explicitly called out and discussed with the user before proceeding.
- Image generation is independent of ordinary chat and uses the existing shared rendering backend as an external dependency; do not implement that integration here. Voice and uploads are out of scope.
- One worker deployable may host several logical responsibilities initially. Do not add separate service placeholders or prematurely split services.
- Deployment-specific behavior policies are not implemented or prescribed by this scaffold. Keep configurable policy content outside shared infrastructure libraries and public documentation.

## Delivery constraints

- pnpm is selected as the repository package manager for contribution tooling, pinned in the root `package.json` (`packageManager` field) and in the committed `pnpm-lock.yaml`. Drizzle with `pg` remains a proposal. No ORM, queue library, numeric policy, database endpoint, or hostname is selected by this scaffold.
- Conventional Commits are validated locally by a `commit-msg` hook (commitlint via Husky, locally installed dependencies only). Validation is local-only: it does not cover squash merge titles, hooks-free clones, or remote enforcement, and no CI or branch protection exists. Unit tests run locally before every commit is created: a `pre-commit` hook (Husky, locally installed dependencies only) runs `pnpm test:unit` — the hermetic unit suite only, never the database-backed integration suites — and blocks the commit on failure; it is likewise local-only and bypassable with `--no-verify`. See [`CONTRIBUTING.md`](CONTRIBUTING.md).
- The future sequence is code/unit tests → feature-branch commit → non-production deployment → integration/end-to-end tests → pre-publication safety checks → push/pull request → owner merge as production approval → automatic production promotion of the same tested immutable artifacts.
- PostgreSQL is an external application dependency, not infrastructure this project manages: the application consumes it, runs its own migrations against it, and this project neither provisions, hardens, backs up, nor operates the database service. Non-production and production still require separate databases, secrets, storage, and side-effect boundaries. Account for restart/order/idempotency testing, application-level migration compatibility between environments, and serialization or isolation of concurrent non-production candidates.
- Provisioned non-production database configuration and personality are authoritative. Routine integration/E2E and release checks must not reset, reseed, restore, replace, or otherwise mutate that configuration; do not run destructive integration suites against any application database. The authorized deployed normal-use smoke may append a uniquely attributable synthetic conversation and retain its traces and normal learned effects as deliberate non-production history; expected retention is not a cleanup failure. Do not automatically delete, rewind, or rebuild conversation, cursor, counters, canonical/shared memory, or relationship state. Legacy deletion/recovery is explicit-only for selected historical markers. Database-backed integration suites that truncate domain data, synthesize runtime configuration, perform destructive migrations, or inject failures are isolated-test tools, not routine ship-it gates; run them only against a positively verified disposable database with run-owned cleanup. No database suite may use production credentials or a production target.
- The delivery flow uses ordinary forward application migrations on the exact candidate and then meaningful normal-use checks through the deployed non-production app with its existing provisioned configuration. Verify configuration invariance using safe metadata/fingerprints without exposing content. Preserve persistent and shared derived state; do not disable memory/personality or delete ambiguous data to force cleanup. If ownership, configuration invariance, required disposable-fixture cleanup, extension availability, or candidate isolation cannot be proved, stop before the affected operation. The disposable local Playwright stack is separate, synthetic, fake chat/decision-provider only, and run-owned; its fixture identity is not the maintained non-production personality.
- Narrow, explicit owner exception to that separation (2026-11-01 decision): the OpenRouter provider API key may hold the same value in non-production and production, each still delivered only through its own per-environment Kubernetes Secret. This is an owner choice, not a default, and it weakens nothing else: the databases, storage, side-effect boundaries, and every other credential (OIDC client secret, session-signing secret, service-to-service tokens, test-gate secret) remain strictly per-environment. The trade-off is documented and accepted: with one shared provider key, spend limits, revocation, and exposure are coupled across both environments — exhausting, revoking, or exposing the key in either environment affects both — and the owner has explicitly accepted that, including the risk that the key in use has been exposed previously.
- A runner-free deployment trigger/controller is unresolved and not running. A merge does not currently deploy. Never claim a deployment or production approval occurred unless verified.
- Local disposable E2E uses a synthetic fixture identity/settings in its run-owned database and fake chat/decision providers; it does not claim to verify the maintained personality. Embedding requests use harmless synthetic inputs and the configured embedding service. Deployed validation is separate and uses the existing provisioned non-production identity, settings, and modules unchanged. An unqualified E2E request in a delivery flow includes the local disposable suite, meaningful deployed normal-use checks, and the guarded deployed smoke; do not skip or weaken a required check. Set a new unique `E2E_RUNS_DIR` outside the historical `tests/e2e/.runs` tree for every local harness or smoke invocation. If a required deployed check cannot safely run or does not pass, stop the delivery workflow and report the blocker rather than proceeding toward a pull request.
- The deployed smoke may invoke an external provider, incur charges, and intentionally retain its non-production conversation and normal learned-state writes. Run it only within an explicitly requested and authorized delivery workflow or on a standalone explicit request. The smoke script's own flags remain required in every context (`E2E_DEPLOYED_SMOKE_ALLOWED=1`, `E2E_DEPLOYED_SMOKE_EXCLUSIVE_DEV_ACCESS=1`); they are runtime safeguards, not a substitute for authorization. Setting the exclusive-access flag records the operator's assertion for that run — it does not manufacture exclusivity — and exclusivity is never a system guarantee. Never claim the system prevents concurrent access or run the smoke when it was not requested.
- No production access or production provisioning is required for scaffold or contract-level work.
