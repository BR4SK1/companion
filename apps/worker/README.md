# Background worker

## Status

Implemented slice: durable grouped conversation work on PostgreSQL, with response-pattern selection through OpenRouter's native typed Decisions API preceding chat generation, plus the private HTTP ingest/read API the web BFF calls. One deployable, modular responsibilities; no image-generation integration, voice, or uploads in this slice. The worker authenticates callers with one service-to-service credential and knows nothing about caller identities: the only identity concept it holds is the owner-authored chat identity/persona text (`chat_identity`) that leads every chat prompt as runtime configuration.

Worker-owned attempt tracing is implemented for conversation turns: every attempt of a turn records its input snapshot (mutable pattern configuration and exact ordered context), the native decision boundary (request before the provider call, outcome after it), and the chat boundary, in relational tables — with a read-only CLI report (`apps/worker/src/cli.ts`) that assembles a turn's full trace. The legacy `conversation_turn.decision` JSONB column is preserved untouched for pre-tracing history and is no longer written by new work.

A long-term memory pipeline is implemented as a second logical responsibility of the same deployable (`src/memory/`): published conversation becomes durable source-linked facts, facts consolidate into observations, vetted observations are promoted automatically under policy safeguards to the canonical recall surface, and temporal summaries plus per-subject profile sheets join canonical recall as one synthetic memory system message per turn. All memory state is relational PostgreSQL (migration `0003_memory_work`) — no JSONB payload, document facade, or EAV for memory content. See [Memory](#memory) below.

## Responsibilities

Implemented in this slice:

- **Private HTTP API.** A cluster-internal HTTP listener (`api/server.ts`) exposes the ingest and read boundary the web BFF calls:
  - `GET /healthz` — liveness (process health only; unauthenticated).
  - `GET /readyz` — readiness (database ping; unauthenticated).
  - `POST /v1/messages` — idempotent user-message ingest. Body `{text, clientKey}` plus an optional `clientSentAt` (the client-reported send time as an epoch-milliseconds integer or an ISO-8601 string; a present-but-unparseable value is `400 bad_request`), which feeds the conversation domain's original-timing provenance (see [Message timing](#message-timing) and [Engagement](#engagement)). The same key with the same content returns the existing message (idempotent replay), and the same key with different content is rejected with `409 conflict`.
  - `GET /v1/thread?limit=N[&before=seq]` — one bounded page of the thread in persisted `seq` order (default 100, maximum 500). Without `before` this is the newest page; with `before` it is the page immediately below that exclusive bound, so a caller walks the full durable history backwards via `page.oldestSeq` until `page.hasMore` is false. The response also carries the worker's startup-captured authoritative IANA timezone (`timezone`, nullable while unconfigured) and a generic status object (`{queued, generating, highestAllocatedSeq, hasRecentFailure}`) with no turn, lease, key, or error internals. `highestAllocatedSeq` is the highest `seq` the thread's identity sequence has allocated — committed-visible, in-flight, or burned (a rolled-back insert never becomes visible) — and, because allocation is contiguous, it bounds what can exist below any page. Consumers reconcile by re-deriving the gaps between their loaded seqs and walking pages downward from each gap's top; the web client does this with a bounded per-cycle budget and no timing assumption (an in-flight seq and a burned seq look identical at any single snapshot, so an unresolved gap keeps its bounded share of probing instead of being discarded on a deadline). `hasRecentFailure` is a durable, sanitized trailing-failure flag — a failed turn claimed after the most recently completed one, or any failure before the first completion; the underlying error text never crosses this boundary.
  - `POST /v1/memory/recall` — the general recall surface: canonical memory recall by arbitrary query, independent of the per-turn chat assembly (whose query is derived from the turn's user text). Body `{query, limit?}`; the response is the recall pipeline's own result shape (query mode and resolved temporal window metadata, ranked fact and observation items with their score components, and diagnostics). Same domain validation as the per-turn path — shape errors are `400 bad_request`, semantic violations are `400 invalid_query`; the route is `405` for non-POST and `503 unavailable` when memory is not provisioned (an unprovisioned deployment is distinguishable from an unknown route). Bearer-token authenticated like every private route; each call records a metadata-only `recall` operation.
  - `GET /v1/engagement` — the engagement domain's current aggregate summary, recomputed on read: the effective state, the last user message's id and effective time, the silence since it, and the configured band cutoffs. `503 unavailable` when engagement is not provisioned (an unprovisioned deployment is distinguishable from an unknown route). Bearer-token authenticated like every private route.
- Every API endpoint requires the `WORKER_API_TOKEN` bearer credential (constant-time comparison); there is no unauthenticated mode — the worker fails closed at startup without it. Failures are generic and sanitized (`bad_request`, `conflict`, `unauthorized`, …); internal details are logged server-side only.
- **Durable message ingestion contract.** User messages are appended to PostgreSQL; a caller-supplied idempotency key makes re-ingestion (e.g. a retried request) a no-op returning the existing message, and reuse of a key with different content raises a typed conflict (`ClientKeyConflictError`) instead of silently rebinding the key.
- **Claim-time grouping.** All pending (unassigned) user messages form a trailing run of the thread; claiming groups the entire run into one turn with one snapshot — never one message at a time.
- **Snapshot semantics.** A claimed turn processes exactly the messages grouped at claim time. Messages that arrive while the turn is in flight stay unassigned and are grouped into the next turn.
- **Prior-turn context snapshot.** The decision state and chat request are built from one coherent snapshot of prior work: the messages of every turn claimed before the processed one, in conversation order — for each turn, its grouped user messages followed by its published reply. Conversation order differs from raw `seq` order exactly where a reply was published after a later user message arrived (that message joins the next turn, so its `seq` is lower than the reply's): the reply still precedes it in context. Unassigned messages (future turns), the processed turn's own messages, and any later turns' messages are excluded — no leakage and no duplication. Because exclusion and ordering are keyed by turn association rather than a raw-`seq` cutoff or lease state, the snapshot is identical on every attempt of the same turn, including after a lease reclaim. A failed turn is terminal in this slice, but its user messages stay part of the visible thread and appear in later context without a reply.
- **Ordered persisted replies.** Processing is serialized (at most one in-flight turn with a valid lease), and each turn publishes at most one assistant reply whose thread position is assigned at publication, so reply order in the thread equals turn order.
- **Restart/lease recovery.** A turn whose lease has expired is reclaimable: the next claim resumes the same turn with a new attempt (incremented) and a fresh lease. A heartbeat renews the lease while the turn is in flight, at one third of the lease (at least 1000ms; configuration enforces a lease of at least 3 seconds so the cadence always renews before expiry — see `apps/worker/src/work/timing.ts`).
- **Attempt tracing.** Every attempt of a turn (initial claim or reclaim) gets one relational trace row, created inside the claim/reclaim transaction, with its terminal outcome (`published`, `failed`, `fenced`, or `superseded`). At meaningful boundaries the attempt records:
  - **Input snapshot** (before the decision step): the mutable response-pattern configuration as it stood (each pattern's full content, in presentation order) and the exact ordered context (prior-turn history plus the turn's grouped messages) the attempt saw. Written in its own fenced transaction, so the snapshot exists even when a later step fails; a second snapshot of the same attempt is a no-op (the first one is what the attempt actually saw).
  - **Decision boundary** (request written before the provider call, outcome written after the call and before the selection step): the native typed request as sent and, once a call resolves, the response as returned — choice, optional confidence, optional per-option probability distribution, response model/provider/id, and usage. Optional native values are nullable columns: absence stays absent, no normalization is applied. The row's `state` tracks the boundary lifecycle: `requested` before the call, then `responded` (the native response), `failed` (the actual transport error, with the truncated response body only when the transport retained one), or `invalid` (a body arrived but failed contract validation; the offending untyped value is not persisted — arbitrary provider data has no relational home) after it. The selection step outcome (`selected`, or `rejected` with its reason) is recorded separately, after the outcome, so a rejected selection still leaves the complete response behind.
  - **Chat boundary** (request written before the provider call, outcome written after the call and before publication): the native typed request (each message linked to its `conversation_message` row; synthetic system messages have no source, and each message carries its assembly-chunk classification — `identity`, `profiles`, `temporal`, `recall`, `article`, `relationship`, `guidance`, or `conversation`, with rows recorded before that classification existed left untyped) and the response as returned — response id/model, choices, usage, and the generated reply content, plus the `chat_identity` revision the request carried. The row's `state` tracks the boundary lifecycle: `requested` before the call, then `responded`, `failed` (the actual transport error), or `invalid` (a body arrived but failed contract validation) after it. A `responded` record carries the application usability verdict separately from the transport outcome: `application_rejection` names the reason the application rejected an arrived response (for example, no choices returned) while the response itself is still recorded in full — the trace stays unambiguous about whether the response arrived and whether the application accepted it. Absent raw data stays absent — an error trace records the real error kind/message/body, never invented content.
  - **Temporal context** (recorded with each chat request): typed columns on `trace_attempt` preserve the attempt's instant, authoritative timezone, local civil date/time, inferred/overridden meteorological season, and eligible occasion keys/text. This is captured afresh per processing attempt and ties back to the exact `temporal` system message stored with the chat request; when timezone or season is unspecified, the row and prompt say so rather than deriving values from the host environment.
  A fenced-out attempt (whose lease was lost to a reclaiming worker) cannot record any trace boundary; the reclaiming worker's claim transaction closes the stale attempt as `superseded` in the same transaction as the lease replacement, so a crashed old worker is counted without depending on its own self-report (a late self-report is a no-op). Trace writes are fenced and idempotent per attempt, and a duplicate record of the same boundary overwrites harmlessly. A fenced write is not ignorable: the composition edge turns the store's `false` result into `TraceWriteFencedError`, so a stale attempt stops processing at the first fenced boundary — no further provider calls, and no selection or publication based on an unrecorded boundary — while the engine handles the lost lease through its existing fenced failure path. The trace is feature-specific and relational: no generic JSONB payload, document facade, or EAV.
- **Read-only trace report.** `apps/worker/src/cli.ts` (`node src/cli.ts <turnId> [--json]`, requires `WORKER_DATABASE_URL`, no provider credentials) assembles a turn's human-readable (or JSON) report: the turn plus every recorded attempt with all boundary records — and, for turns created before tracing, presents the legacy `conversation_turn.decision` JSONB clearly marked as legacy. The report is assembled inside one read-only repeatable-read transaction on a single pooled client, so the turn row and every attempt and boundary row come from one consistent committed snapshot even while publication or failure finalization commits concurrently; the server enforces read-only, so the report can never write. Publication is reported only from the turn's actual status (`reply published: yes/no`), never from a boundary record; the chat boundary's reply content is rendered as the *generated* reply, with any application rejection shown separately. The CLI only ever reads.
- **Fencing.** Publication, decision-diagnostics recording, and failure recording are all conditional on the turn still being in flight under the caller's lease. A stale worker that lost its lease can neither publish a reply nor overwrite the state of a reclaiming worker.
- **Idempotent publication.** Publishing completes the turn and persists the reply in one transaction; a duplicate publication attempt after success is recognized and reported as a no-op.
- **Response-pattern decision.** When enabled `response_pattern` records exist, one `choice` question is asked through the OpenRouter Decisions API (`POST /api/alpha/decisions`): options are pattern ids, each described by its **selection description**. The returned top choice selects the pattern. The choice answer is preserved as returned (including optional probabilities/confidence) and recorded on the turn as diagnostics; an answer that does not name an offered pattern is an error, not a silent fallback. With no enabled patterns, the decision step is skipped and chat runs without guidance.
- **Chat generation.** The prompt is assembled modularly and deterministically from typed chunks, each synthetic section its own system message, in a fixed order: the owner-authored **identity** (required, from `chat_identity`), then the optional **generated subject profiles**, **current local temporal context plus temporal memory**, **long-term recall**, **article**, and **relationship/familiarity** chunks, then the selected pattern's **response guidance** (absent when no pattern was selected), followed by the prior-turn context snapshot and the turn's grouped messages. Current date/time uses the startup-captured authoritative IANA timezone; the prompt receives a freshly computed local civil date/time and conservatively inferred meteorological season for each attempt, plus deterministic, non-presumptive upcoming holiday/birthday context when eligible. The request goes to OpenRouter's Chat Completions API (non-streaming).
- **Chat identity.** The identity/persona text is owner-authored runtime configuration in the `chat_identity` table (one singleton row with a revision counter), like `response_pattern`: provisioned per deployment, never seeded by migrations, and never code or repository content. It is read fresh per turn, so owner edits apply on the next turn, and every chat boundary trace records the revision it used. Missing or empty identity is a fail-closed `IdentityConfigurationError` that fails the attempt before any snapshot, decision, or provider call — the prompt is never assembled with an invented persona.
- **Long-term memory pipeline.** When enabled, published turns feed an ingest watermark that extracts facts, consolidates them into observations, and (under safeguards) promotes them to a canonical recall surface automatically; temporal summaries and per-subject profiles are generated on schedules; and one synthetic memory system message (profiles, then temporal context, then canonical recall) joins the chat request after guidance. Memory operations are traced as metadata only. Full description in the [Memory](#memory) section.

An engagement domain is implemented as a third logical responsibility of the same deployable (`src/engagement/`): deterministic per-message engagement assessments and a recomputed effective state, driven only by user-message timing. See [Engagement](#engagement) below.

An article-ingestion domain is implemented as a fourth logical responsibility of the same deployable (`src/articles/`): PostgreSQL-configured RSS/Atom feed ingestion that produces real assistant-attributed memory facts from article reactions. Feeds, policy limits, persona prompts, and the model are personal configuration in relational tables (`article_feed`, `article_behavior`, `article_prompt`), reloaded and validated at every attempt — an unprovisioned deployment logs exactly `ingestion not configured` and the attempt returns before any fetch, provider call, or state write, and provisioning later takes effect without a worker restart. Excerpts (never full pages) are fetched with bounded, SSRF-hardened networking: address-aware literal checks, pre-connection resolved-address validation, and a pinned connector whose connect-time DNS hook re-validates every resolved address and pins the connection to exactly those validated addresses, so there is no DNS-rebinding window between validation and connection., reactions are generated and reviewed through the provisioned persona prompts, and an accepted reaction becomes a real memory fact attributed to the assistant subject, linked to its article source. Full description in the [Articles](#articles) section.

A generic relationship/familiarity domain (`src/relationship/`) is implemented as an optional fifth logical responsibility. Its relationship type, local behavioral-day boundary, tiers, thresholds, behavioral prompts, question bank, and extraction instructions are runtime-only relational configuration; migrations create structure but seed no settings or question content. It adds a separate chat context chunk and learns current user/assistant interpretations only from the new turn; it does not backfill history or expose a new API.

A generic routine/schedule domain (`src/routine/`) is implemented as an optional sixth logical responsibility. Runtime-only recurring schedule transitions define arbitrary locations, activities, availability, and optional interaction context; durable scheduled and applied state plus unavailable-period notice events are reconciled independently of chat. When provisioned, new user turns are held until the configured schedule is available, while an already-claimed turn is allowed to finish. Each ongoing planned unavailable period produces one factual assistant notice in the same continuous thread; it is a schedule event, not a user turn or a general proactive-chat facility.

Not implemented in this slice (by design): image generation, segmentation timers, non-schedule proactive follow-up, retries for failed user turns, and multi-conversation support. Memory import/backfill tooling for pre-existing conversation history is likewise not implemented, and the ingest cursor is new-turn-only: the first ingest pass after enablement starts at the newest existing completed turn, so pre-existing history is never processed retroactively.

## Work model and guarantees

Turn states: `in_flight` → `completed` | `failed`.

- **Grouping rule.** `claimNextTurn` atomically (one transaction, serialized by a PostgreSQL advisory lock): reclaims the oldest expired in-flight turn if any; otherwise refuses to claim while an unexpired in-flight turn exists; otherwise groups the entire unassigned trailing run of user messages into a new in-flight turn with a fresh lease. A message ingested after the grouping `SELECT` is not part of the snapshot. Message ingestion takes the same advisory lock inside its transaction, so ingest commit order matches `seq` order (PostgreSQL sequences are not transactional) and a claim never snapshots while an ingest transaction is in flight — a later-seq message can never be claimed ahead of an earlier one. Ingestion is short; briefly waiting behind a claim transaction is acceptable.
- **Fencing rule.** Publication, decision-diagnostics recording, trace recording, and failure recording are all fenced: turn-state transitions and reply publication require `status = 'in_flight' AND lease_owner = <caller> AND lease_expires_at > now()` inside the publishing transaction. Expired-lease claims increment `attempt` and replace the lease owner.
- **Ordering rule.** Serialized claims mean persisted replies appear in thread order across turns; the assistant reply to an earlier group appears after any user messages that arrived while it was being generated (normal messaging semantics; the visible thread stays continuous).
- **Exactly-once honesty.** Publication and turn-state transitions are exactly-once (fenced, idempotent). External provider calls are not: a crash between a provider call and publication replays that call after reclaim. Only one reply ever survives per turn, but a replayed call can incur duplicate provider cost. Leases also mean an unclean worker restart waits up to one lease period before reclaiming its own turn (worker identity is not persisted in this slice).

## Memory

The memory pipeline turns published conversation into durable, source-linked long-term memory and feeds it back into chat. Every stage is durable and idempotent on its own; every LLM task goes through the same shared OpenRouter transport with its own typed prompts; every stage records a metadata-only operation trace.

- **Ingest (watermark, new turns only).** A watermark (`memory_ingest_state`) walks completed turns in order. The cursor is new-turn-only: on first use after enablement it is initialized at the newest existing completed turn (or at "nothing yet"), and only turns published after that are ever extracted — enabling memory never backfills pre-existing history, and the guarded initialization is race-safe against concurrent attempts. A completed turn is extracted only after it has settled (`WORKER_MEMORY_INGEST_SETTLE_MS`); a turn-complete trigger and a reconciliation timer both feed the same pass, capped at `WORKER_MEMORY_INGEST_MAX_TURNS` turns per run. Per-turn extraction results are cached (`memory_turn_extraction`/`memory_turn_extraction_item`), so re-running over an already-extracted turn is a no-op. Fact extraction is batched (`WORKER_MEMORY_FACT_BATCH_TURNS`, `WORKER_MEMORY_FACT_BATCH_MAX_CHARS`) and writes `memory_fact` rows with per-message source links (`memory_fact_source_message`).
- **Consolidation.** When enough new facts have accumulated since the last run (`WORKER_MEMORY_CONSOLIDATION_NEW_FACTS_THRESHOLD`) or on the interval timer (`WORKER_MEMORY_CONSOLIDATION_INTERVAL_MS`), recent facts are consolidated into observations (`memory_observation`) with evidence resolved to fact ids (`memory_observation_evidence`) and explicitly reported omissions (`memory_observation_omission` + `memory_observation_omission_evidence`), inside a run record (`memory_run`/`memory_run_turn`). Evidence links resolve against durable production facts rather than a run-scoped copy, so evidence stays stable and verifiable across runs. Artifacts are per-run and immutable: a re-run over the same source window writes its own artifact rows under a stable logical observation-set identity and never deletes another run's artifacts or evidence, so provenance survives re-runs and failures. Each artifact row and its evidence links commit in one transaction — and each omission row commits together with its supporting/contradicting fact evidence, so aggregate provenance is never missing while the omission exists. Ingest accounting is atomic with the fact write: the fact batch, its source links, the watermark advance, and the `new_facts_since_consolidation` counter commit in one transaction, so a crash between "facts durable" and "accounting advanced" cannot permanently under-count (which would starve consolidation through the zero-fact guard); a replay either sees both or neither. The counter is maintained with atomic relative increments and decrements, so concurrent ingest passes cannot lose counts, and a run consumes exactly the count it observed at entry.
- **Automatic promotion.** When enabled (`WORKER_MEMORY_AUTOPROMOTE_ENABLED`), observations that pass the policy safeguards (`policy.ts`: support/evidence-strength checks) are promoted to the canonical recall surface (`memory_canonical_observation`) automatically. Promotion plans and items are recorded (`memory_promotion`/`memory_promotion_item`) with a plan content hash, and promotion is idempotent: re-promoting an already-promoted observation is a verified no-op. Promotion is automatic-only: there is no manual promotion path, no reviewed-exception input, and no reactivation switch — inactive canonical identities are never reactivated by promotion. Planning EXCLUDES an eligible artifact whose canonical identity is already inactive (summary `inactiveCanonicalSkipped`), so one retracted identity can neither reject the whole run nor block its unrelated observations. Each item applies in its own transaction under a row lock with a mutation-fence compare-and-swap (bumped by every canonical mutation, including retractions). Item outcomes are settled-checked in order under the lock: an item this promotion already applied stays `applied` (its history event and document commit together; a retraction that landed after that apply is never restored), an item whose identity a LATER promotion already advanced is `superseded` (the later content stands untouched, no history event of its own), and only then is a concurrently retracted identity recorded as `skipped_inactive` — so unrelated eligible items always apply. The plan is staged before applying; manifest recovery is manifest-first: an existing `staged`/`applying` manifest is resumed from its immutable staged items and a `completed` manifest is verified against its original stored plan hash and history — never re-planned (a replan after concurrent state changes could mis-mark recovery as "nothing eligible" or reject finished work); post-apply verification accepts applied items status-agnostically (history event present, document at or beyond this promotion's sequence). At the end of every ingest pass — independent of extraction success — the runtime reconciles completed runs that lack a completed promotion, bounded, with a five-minute backoff for runs whose latest promotion attempt failed and a fair retry order keyed by each run's latest attempt (never-attempted runs by completion), so repeatedly failing runs rotate out of the batch instead of starving pending runs behind them. Retraction (manual or policy review) is atomic: one transaction re-reads the row `FOR UPDATE`, re-decides (apply / replay no-op / never overwrite a manual decision), appends the history event, and guarded-updates the row — a crash leaves neither an orphan event nor a partial state, and competing retractions serialize. Policy-review retractions are additionally fenced to the reviewed snapshot (revision and content hash): an observation a concurrent promotion revised after the plan was built is skipped as stale for the next review to re-plan, never retracted on stale evidence. Every status change is preserved in `memory_observation_history`.
- **Canonical policy review.** A review re-derives every selected canonical observation's decision from its current evidence and the promotion policy, applied in reverse: an observation whose evidence no longer satisfies the policy (event-specific temporal anchor, single-turn evidence, habit/conditional-pattern recurrence breadth) becomes a `policy_retract` candidate with reason codes; incomplete provenance (a referenced fact that no longer resolves) requires manual review instead. Applying a plan is always an explicit two-step act — the dry run prints a plan hash and confirmation token, and the apply requires that exact token, so state drift between plan and apply is rejected. No scheduler runs this. The `memory-cli` (`apps/worker/src/memory-cli.ts`, `WORKER_DATABASE_URL` only) exposes `observations` (inspection), `review` (dry-run plan / token-confirmed apply), and `report` (a read-only automation report over metadata-only operations, promotion outcomes, consolidation runs, and canonical state counts for a UTC window).
- **Recall.** Canonical recall ranks by PostgreSQL full-text match (`websearch_to_tsquery` against a GIN-indexed tsvector over claim/condition/consequence, OR-joined sanitized tokens) plus a recency score (`WORKER_MEMORY_CANONICAL_RECENCY_WEIGHT`, `WORKER_MEMORY_CANONICAL_RECENCY_HALF_LIFE_DAYS`), drawn from a bounded candidate set (`WORKER_MEMORY_CANONICAL_CANDIDATE_LIMIT`) and rendered under a character budget (`WORKER_MEMORY_RECALL_MAX_CHARS`). The per-turn recall query is the first 16 whitespace-separated words of the turn's user text, capped at 512 characters. An explicit temporal expression in the query switches recall to timeline mode (evidence inside the named window, ranked by observed time) or hybrid mode (window AND full-text match when keywords remain). Temporal parsing follows the pipeline's documented date-parser grammar with the calendar fixed to the CONFIGURED behavioral timezone (never hardcoded, never UTC): explicit `between/from … and/to …` ranges, `last|this|next <weekday> [morning|afternoon|night]`, `today|yesterday|tomorrow [part]`, `last|this morning|afternoon|night` (local hours 4/12/17, night ends 04 next day), `last|this week|month` (Monday-based weeks), and absolute tokens (`YYYY-MM-DD` or `<month> <d>[, <yyyy>]` in the reference year). Deliberate non-features: no bare month, no bare year, no `YYYY-MM` token (the ordinary word "may" stays a keyword), and no preposition stripping in the remaining query. The temporal phrase is removed from the full-text keyword source, so "what did I do yesterday" searches for "what did I do". Unsupported or ambiguous date-like phrasing, invalid dates, and over-two-years ranges stay in keyword mode (unchanged behavior); when no behavioral timezone is configured, temporal detection is disabled entirely and every query is keyword mode. The resolved mode and window are reported in the recall response's query metadata.
- **Temporal memory.** Behavioral day/week/month/year summaries (`memory_temporal_summary`, with source-message links, selection pair ids, and segment pair counts) are generated and refreshed on a reconciliation timer (`WORKER_MEMORY_TEMPORAL_RECONCILIATION_MS`) and injected as chat context. A cached summary is served with its provenance read back from storage (the summary's selection columns and the source-message links table), so aggregate provenance survives caching instead of being silently emptied on the cache path. The local timezone is the worker-wide `companion_time_settings.timezone`; memory keeps its separate behavioral-day start hour in `memory_behavior`. The boundary accepts IANA zones including DST transitions; missing/invalid timezone or missing memory boundary leaves the memory feature fail-closed. Historical summary timezone values are retained as generated.
- **Profiles.** Two pipelines: profile v1 distills per-subject sheets from temporal day summaries (`memory_profile_summary`), behind its own flag (`WORKER_MEMORY_PROFILE_SUMMARIES_ENABLED`, default off — the chat prompt does not consume v1 sheets, so defaulting it on would make billable calls with no consumer); profile v2 distills observation profiles from the canonical observation set (`memory_observation_profile` + `memory_observation_profile_claim` + `memory_observation_profile_source`). Profile v2 is scheduled at a configurable local hour (`WORKER_MEMORY_PROFILES_GENERATE_HOUR`) in the provisioned behavioral timezone. Each subject's v1 system prompt carries that subject's provisioned evidence-attribution rule (`memory_subject.profile_evidence_rule`). Regeneration is fingerprint-gated in both pipelines: a profile is regenerated only when its inputs changed — and the fingerprint binds to the FULL actual prompt (base plus the subject's evidence rule for v1), so a rule change invalidates the cached sheet. Claims the model omits are backfilled from the observation set. The v2 fingerprint additionally binds to the generation-affecting configuration (model and output-token cap), and the serve gate checks the stored document's prompt version, prompt content hash, and model against the currently serving configuration — a DB edit of the same-version prompt row or a changed model suppresses the stored document until regeneration. The v2 serve gate also checks the FULL relational input set (`memory_observation_profile_source`: every observation rendered into the prompt, each with its revision and content hash at generation time), not just the claims the model happened to emit — the document is suppressed unless every source is still active with an unchanged revision and content hash, so a concurrent retraction of even an unclaimed source (or a content revision of any source) suppresses stale prose until the next regeneration; a profile save whose observation set moved while the LLM call was in flight is skipped, so a concurrent generation cannot restore prose citing retracted sources. Temporal summaries carry the same generation binding (their fingerprint includes the model) and the prompt-context validity check additionally requires the stored model and prompt content hash to match the serving configuration. Generation signatures and fingerprints across the pipeline bind to the actual prompt content (hashed), not just a version label, so re-provisioning a same-version prompt invalidates caches and fingerprints.
- **Chat integration.** When memory is enabled, the turn processor sends the enabled subjects' v2 observation profiles (fingerprint-tagged XML blocks), recent temporal memories, and canonical recall results as separate synthetic system messages — one chunk each, after identity and before the response-guidance message — with the profiles chunk kept separate from the per-turn recall output because it is a separately generated, fingerprint-gated document. The chat prompt consumes recent temporal leaves plus v2 profiles only; v1 profile sheets are a separately generated artifact (see Profiles) and are not part of the chat message. Each section degrades independently: a failed section logs a warning and the turn continues with the rest, and a section that rendered nothing contributes no chunk. In the chat trace each memory message is recorded with a null message source plus its chunk classification. That trace is an exact request snapshot by design, so the rendered memory text (profile sheets, temporal summaries, recall lines) is duplicated in `trace_attempt_chat_message` — acknowledged duplication, not an accident: the memory operation trace (`memory_operation`) stays metadata-only, and the duplicated text lives under the same database and access boundary as the memory tables themselves. Memory-domain prompts and completions are never logged anywhere with `logPrompt`-style capture; only this chat-request snapshot carries rendered memory content.
- **Operation tracing.** Every memory operation (ingest pass, consolidation, promotion, temporal sweep, profile generation, recall) is recorded in `memory_operation` as metadata only: operation kind, outcome, timing, and referenced row ids such as the ingest watermark or run id. No prompt or completion content is stored — the memory trace cannot become a shadow copy of conversation content.

Scheduling is in-process: timers plus serial in-process queues; durability lives in the watermark, the extraction cache, and fingerprint state, never in queue memory — a restart re-derives everything from the database. Queued work coalesces per concern (at most one pending ingest pass and one pending temporal sweep), so timer ticks arriving during a pass collapse into the next pass instead of accumulating. An interval-triggered consolidation is skipped while no new facts have arrived since the last run, avoiding pointless re-derivation of an unchanged window. Durable memory diagnostics (operation-trace details, `memory_run.error`, memory log lines) record FIXED error categories — transport kind with a trusted numeric HTTP status (`llm_timeout`, `llm_http_status_429`, `llm_network`, `llm_invalid_json`), typed output-validation and attribution failures, Postgres SQLSTATE codes (`db_23505`), configuration and internal fallbacks — and never error message text: error messages are arbitrary text that can carry provider-response or model-derived private content, and no redaction heuristic is trusted against that. Profile generation shutdown awaits the in-flight pass, so stopping the worker never abandons a half-finished profile write. Ingest is additionally triggered by `onTurnPublished` after a successful publication only. A pipeline stage that fails is retried by the next timer tick, not abandoned.

Every memory LLM task runs with the pipeline's task presets — per-task temperature, output-token caps (consolidation and profile v2 caps are configuration; the rest are fixed), a reasoning-effort knob (`high`, or `max` for consolidation), and a thinking flag — mapped onto the OpenRouter request as `reasoning.effort`, `include_reasoning`, and (for Claude-family models only) `extended_thinking`. Reasoning tokens count against `max_tokens` on GLM 5.3 Flash, so every cap covers reasoning plus visible output. Two provider-error fallbacks are applied in a fixed order: a structured-output rejection drops `response_format`, and a reasoning-clamp rejection retries at `reasoning.effort: "low"`.

Personal behavior configuration — subjects (including each subject's v1 evidence-attribution rule), persona prompt text, behavioral-day start hour, the worker-wide timezone, and chat identity — is runtime configuration like `response_pattern`: it lives in the `memory_subject`, `memory_prompt`, `memory_behavior`, `companion_time_settings`, and `chat_identity` tables, is provisioned per deployment, and is never seeded by migrations or shipped in code or documentation. Loading is fail-closed: a missing required prompt row, an empty subject table, a missing evidence rule, or a missing/invalid behavioral boundary is a configuration error; a missing or empty chat identity fails the turn as an `IdentityConfigurationError` (chat cannot run without the owner-authored persona, and no persona is invented in its place).

Rollout is provision-then-restart: when `WORKER_MEMORY_ENABLED` is on but the personal configuration is not yet provisioned, the worker starts normally and runs memory as a safe no-op (a warning names the missing configuration; no memory scheduling, execution, or provider calls happen). Provision the tables and restart the worker to enable memory. Any other configuration failure (for example, an unreachable database) is still a startup failure.

## Engagement

The engagement domain (`src/engagement/`) derives a deterministic engagement state from user-message timing alone. It is the third logical responsibility of the same deployable, a domain peer to memory: typed relational data owned by the domain, no timers, no proactive behavior, and no consumption by the response-pattern decision or the chat prompt in this slice (deliberate — engagement is recorded and served; other domains are not yet readers of it through any decision input).

- **Message timing.** Engagement reads the conversation domain's **effective message time** (`effective_at`), which the conversation store derives and persists at ingest from dual provenance — see [`src/conversation/timing.md`](src/conversation/timing.md). Both clocks are always recorded: the raw client-reported send time (`client_sent_at`, nullable — absence is legitimate) and the server receive time (`server_received_at`, the database clock, kept honest and identical to the effective time on every fallback). The effective time is the client time when it was present, parseable, within the configured ahead-tolerance of the server clock, and not below the monotonically tracked acceptance/order bound (the maximum effective time recorded so far on user messages — a candidate below it is rejected as `out_of_order`, equality allowed; the bound gates candidate validation only and never modifies a chosen value). For every other status the effective time is the ACTUAL recorded server receive time — never clamped or otherwise modified, and no synthetic effective timestamp is ever produced. The choice and its reason are persisted per message (`time_source` = `client`/`server`, `client_time_status` = `absent`/`valid`/`future_skew`/`out_of_order`/`invalid`), preserved independently so absence and unparseable values stay distinguishable. This is provenance, not a claim of the perfect original send time — skew and delay are recorded, never corrected; an accepted client time may sit ahead of later receipts, so the effective timeline is advisory and consumers treat negative gaps defensively rather than the store fabricating monotonicity. Idempotent replays return the originally recorded values untouched: a retry never re-classifies the client time and never re-assesses engagement. Assistant messages carry no client time and never move the engagement clock. Client times arrive through `POST /v1/messages`'s optional `clientSentAt` and the web client sends its own stable send-time value across retries.
- **Per-message assessments.** When a NEW user message is inserted, the engagement store runs inside the conversation store's ingest transaction (the advisory-locked serialized section, on that transaction's own client) and records one assessment row in `engagement_message_assessment`: the assessed band of the silence between this message and the immediately-preceding user message, the previous message's recorded assessment state, the silence duration, the message's effective time, the band cutoffs the assessment used, and a marker for the first-message-after-a-lull retention rule. The write commits atomically with the message. Assistant messages and idempotent replays never create or modify assessments, so user activity is never reset by them. Because assessments are persisted values (including the cutoffs snapshot), a grouped turn reads the assessment of its actual last user message — or that message's recorded absence, never an earlier message's assessment — stable across retries and lease reclaims, and later band-configuration changes never rewrite history.
- **No-immediate-engagement rule.** The first user message after a lull assesses `lull` (its preceding silence is in the lull band); a subsequent message arriving within the engaged band assesses `engaged`. This is not a special case — it falls out of assessment = band(silence) — but it is the semantic reason the effective state is floored (below) instead of simply tracking the newest message.
- **Effective engagement (last-activity clock with an assessment floor).** There is no mutable "current engagement" row. The effective state is always recomputed on read as the **deeper of** the activity band (silence measured from the LAST user message's effective time — every user message moves this clock) and that message's own recorded assessment, which acts as a retention floor. So: inactivity transitions always measure from the last user message (a reader observing the thread two minutes after the last message sees an engaged-band silence, never a stale deeper band); the first message after a lull keeps the state at `lull` (a single return message never overwrites the effective engagement to `engaged` — it lifts only through a message assessed inside the engaged band, i.e. sustained exchange); a message arriving in a deeper band keeps that deeper state until the next message; and pre-engagement history (no recorded assessments) falls back to the pure activity band. Formally `state = deeper(band(now − lastUser.effectiveAt), lastUser.assessment.state)`. Recomputation on read is also what advances the state during silence, recovers after restarts, and fences stale callbacks automatically: nothing mutates engagement state from a timer, and no reader can overwrite a newer state because there is nothing to overwrite. Engagement never triggers proactive messages on its own.
- **Band configuration.** The band cutoffs are runtime configuration in the `engagement_bands` table — exactly like `memory_behavior`: one singleton row, provisioned per deployment (SQL by the operator), never seeded by migrations, never code or repository content (no code default exists), and deliberately not environment variables. The contract is exactly THREE strictly increasing positive cutoffs delimiting the FOUR half-open bands (`engaged` below the first cutoff, then `lull`, `idle`, and `gone` at or beyond the third); each cutoff is the silence at which the next deeper band begins, and every boundary belongs to the deeper band. A non-monotone configuration is rejected. Loading is fail-closed in the safe direction: an unprovisioned deployment starts normally and runs engagement as a no-op (a warning names the missing configuration; no hook wiring happens, and the summary route answers `503 unavailable`). Provision the table and restart the worker to enable engagement. Changing cutoffs changes future assessments; recorded assessments keep the values they were computed with.
- **Transport.** `POST /v1/messages` accepts the optional client send time (see Message timing); `GET /v1/engagement` returns the recomputed aggregate summary (state, the last user message id and its effective time, the silence since it, and the configured cutoffs). The BFF's worker client exposes the same summary read; no browser-facing engagement route exists in this slice.

## Relationship and familiarity

The relationship domain (`src/relationship/`) is an optional, generic chat-context and learning capability. It is owned by the worker and uses the existing effective message timestamps and the same `behavioralDay` implementation as memory; no owner identity, tenant, or additional conversation/thread boundary is introduced.

- **Runtime configuration.** `relationship_settings` holds the configured relationship type, its distinct behavioral-day start hour, bounded tier-movement rule thresholds, answer-extraction instruction, and clarification guidance. The timezone for relationship streaks comes from `companion_time_settings`, the same authoritative worker-wide setting used by memory and routine. `relationship_tier` holds ordered familiarity thresholds, labels, prompts, and behavioral guidance; `relationship_question_type` holds configurable type-level interpretation guidance; `relationship_question` holds the shared question bank, type and tier association, and enabled state. The feature is enabled only when settings, a valid tier set (first threshold zero; strictly increasing thresholds/positions), and at least one enabled question are present and valid. Missing settings or invalid/incomplete config logs a safe actionable warning and disables only this feature; chat continues with no fabricated context or answer update. Configuration is loaded at worker startup; provision or repair it and restart. Migrations contain schema only — no relationship types, tiers, questions, prompts, or personal values are seeded or documented here.
- **Day semantics.** The first recorded conversation date is the behavioral date of the lowest-`seq` message's persisted `effective_at`. User-activity dates for streaks use only user messages (assistant messages do not reset the activity clock), with the configured IANA timezone and day-start hour via `behavioralDay`. The active-day streak counts consecutive activity dates ending at the latest activity date (which may be yesterday); the missed-day streak is the count of behavioral-day boundaries from that latest date to today. With no user activity both streaks are zero. `timeKnownDays` is the non-negative behavioral-date difference from the first recorded conversation date to today. Future-effective user messages are ignored for streak calculation until their behavioral date arrives. PostgreSQL derives distinct local behavioral dates using the configured timezone and local day-start hour (local civil-time subtraction preserves the same DST/day-boundary classification); only those distinct dates, not every message timestamp, cross into application code. The database still scans user activity history to produce the set; a persisted/config-specific activity-day index or summary would add write/storage and refresh complexity and can become stale when timezone/day-start configuration changes, so no extra index or history table is introduced. PostgreSQL and Node ICU carry separately versioned timezone data, so an upstream timezone-rule change can temporarily produce a different civil date until both runtimes' timezone data are updated.
- **Familiarity and tiers.** Each enabled question contributes two eligible slots (one per participant). Base familiarity is current answered slots divided by eligible slots, including clarification-needed interpretations as answered slots. The base tier is the highest configured minimum-familiarity threshold met. Optional configured movement uses time-known plus active streak to move at most one tier up, or missed-day streak to move at most one tier down; the downward signal takes precedence. With movement disabled or no qualifying signal, effective tier equals base tier (`locked`). Absence does not clear answers or lower base familiarity; it can only affect the configured effective-tier signal.
- **Answer learning and clarification.** After a valid assistant reply, an extractor considers only the grouped new user messages and that reply against the configured shared question bank. It separately prepares the current interpretation for `user` and `assistant`; those updates are upserted into the single `relationship_answer` table, keyed by question and participant, inside the same publication transaction as the reply. A fenced or failed publication cannot change answers, and an answer-write failure rolls back only the optional writes while allowing reply publication. Omitted slots are untouched, so absence never erases a learned answer; ambiguous/conflicting evidence is represented by the model's best current interpretation plus `clarification_needed`, not a candidate/revision system. Clarification flags and configured guidance are rendered in a separate relationship system chunk so the assistant can ask naturally when relevant. This is new-turn-only; no historical answer backfill occurs. A configured turn uses the existing memory LLM adapter/model for an additional extraction call after chat; extraction failure is logged without blocking reply publication. No answer content is logged by the feature.

## Routine and schedules

The routine domain (`src/routine/`) is an optional generic schedule and context capability. It uses no fixed location, activity, persona, relationship, or message wording; migrations contain relational structure only and never seed settings, transitions, or interaction content.

- **Runtime configuration.** `routine_settings` stores optional configured departure context; the weekly schedule uses the worker-wide IANA timezone in `companion_time_settings`. Enabled `routine_transition` rows are weekly local-time state changes (ISO weekday, local minute, nullable location/activity, required availability, and optional reactive interaction context). A transition replaces the complete scheduled state; omitted location/activity values mean unspecified. Variations are explicit, owner-configured transitions rather than runtime random choices. At least one enabled transition is required when settings exist. Missing settings keep ordinary chat available and omit routine context. A present but invalid configuration fails closed rather than guessing that the companion is available. Provision or edit configuration in PostgreSQL. Schedule rows reload for evaluations, while a timezone edit is captured by all worker time consumers only after a controlled restart; old routine occurrences and announcements retain their recorded instants/timezones. Do not put actual configured values in migrations, code, or public documentation.
- **Time semantics.** Recurrences use the configured timezone's local civil weekday and minute, independent of host timezone. At a fall-back fold the first occurrence is selected; a local minute in a spring-forward gap shifts forward by the size of that gap (for example, 02:30 becomes 03:30 for a one-hour gap). Availability checks use database transaction time, and scheduled transitions are evaluated directly at claim time so a timer delay cannot admit a new turn after the schedule says unavailable. Admission, scheduled projections, and reconciliation each load settings and enabled transitions together in one SQL statement, so each evaluation uses one coherent configuration revision. An evaluation already past that read uses the revision it read; if an edit commits afterward, the next evaluation observes it. Related settings and transition edits that must act as one revision (for example, changing timezone together with schedule rows) must be committed atomically by the operator; there is no coordinated configuration-write protocol. Schedule and transition edits affect live admission and scheduled projections immediately; a worker-wide timezone edit takes effect only after a controlled restart. Reconciliation uses the current schedule configuration for occurrences beyond its applied cursor. Applied occurrence history is immutable by `(transition_id, local_date)`: an edit does not rewrite an event already recorded for that identity, and `routine_applied_state` continues to match persisted applied history rather than the live projection.
- **Scheduled and applied state.** The current schedule projection is distinct from `routine_applied_state`, which advances only through the durable reconciler. Each applied occurrence is appended to `routine_applied_transition`. Per-turn routine context is a read-only as-of projection: it selects the latest applied occurrence recorded by the attempt reference instant and never reconciles or mutates announcement lifecycle state. Reconciliation runs at startup and periodically without depending on chat; every pass catches up all recurring transitions after its persisted cursor in chronological order. A crash commits each occurrence and state together or neither, and concurrent reconcilers serialize on a routine-owned advisory lock. The same reconciliation tracks a typed `routine_announcement` event for each unavailable period, with its own UUID identity rather than a transition/date key so a genuine same-day re-entry can receive a distinct event. Periods that become available are recorded as ended; stale pending events are cancelled. Editing an announced unavailable start forward does not by itself count as an observed available interval or duplicate the notice. Pending events are revalidated under schedule, routine, and conversation locks, and their published state plus linked assistant `conversation_message` commit atomically. The publisher samples the database clock only after those potentially blocking locks and row waits; if the configured return boundary has passed, it cancels instead of inserting. Duplicate passes, concurrent workers, and restarts cannot duplicate an active period's notice. Recovery publishes a truthful late notice only while the same absence remains ongoing, with configured start/next-available times; ended absences are not replayed. Notice content is deterministically composed from the validated schedule and optional configured departure context, so no provider or chat-identity call is required. A database outage prevents publication; retries occur while the absence remains current, with no promise if infrastructure remains unavailable through the period's end and no claim that the user read the message. The chat context presents scheduled, applied, and next state separately.
- **Availability-aware queue.** The optional gate runs inside the existing claim/ingest advisory-locked transaction and only before a new user turn is grouped. Existing expired in-flight turns are recovered first even if the schedule is unavailable, preserving work already claimed while available. Unassigned user messages remain durable, grouped, and ordered until the next available claim; there is no maximum wait or interruption bypass. A schedule notice is a separate assistant-only message: it takes the same short conversation serialization lock, never claims or answers queued user work, and waits until any in-flight turn has completed its publication before it inserts the notice. Schedule admission remains closed independently, so the waiting notice cannot release queued user messages. Assistant publication shares that serialization point so message order is deterministic. No lease is held while waiting for availability, and existing user-turn leases, heartbeat, fencing, and attempt traces are unchanged.
- **Notice content and timing.** Routine chat context reports state and configured interaction context but does not repeat departure instructions; the independent notice announces only validated schedule facts plus optional owner-configured departure context. Its typed event links to the normal thread message. A notice may arrive late after infrastructure recovery only while that same unavailable period is still active; pending notices for ended or edited-away periods are cancelled rather than replayed. If the database cannot publish during the entire absence, no notice can be guaranteed. The thread API records durable publication only; it has no read receipt or proof the user saw it.

## Articles

The article domain (`src/articles/`) is the fourth logical responsibility of the same deployable: RSS/Atom feed ingestion that produces real assistant-attributed memories. It reuses the memory pipeline's storage (`memory_fact`), LLM caller, and metadata-only operation tracing rather than adding a service boundary; its persona-bearing prompt text lives in the database, and code owns only the mechanical envelope (fetch bounds, parsers, state machine).

- **Configuration contract.** Feeds (`article_feed`), policy limits and model (`article_behavior`), and persona prompts (`article_prompt`) are personal deployment configuration provisioned in relational PostgreSQL — never code constants, never environment variables, and never seeded by migrations. Configuration is loaded and validated at EVERY attempt: a missing or incomplete configuration (no behavior row, no enabled feed, a required prompt row absent) logs exactly `ingestion not configured` and the attempt returns before any feed fetch, provider call, or article-state write; the runtime keeps polling, so provisioning (or editing) the tables takes effect on the next attempt without a restart. A behavior row with `enabled = false` is a distinct disabled state (`ArticleDisabledError`), and a present-but-invalid value (malformed URL, out-of-range limit) is a distinct invalid state (`ArticleConfigurationInvalidError`) — never silently ignored and never conflated with missing. Limits are clamped against hard code-side caps so a bad row can never unbound a run.
- **Bounded fetching (`rss.ts`).** Only http(s); URLs with embedded credentials are rejected; host checks are address-aware: IPv4 and IPv6 literals are parsed in full and the loopback, unspecified, private/CGNAT/broadcast IPv4, embedded-IPv4 IPv6 forms (IPv4-mapped `::ffff:0:0/96`, IPv4-compatible `::/96`, NAT64 `64:ff9b::/96`, whose embedded address runs the IPv4 checks), link-local (`fe80::/10`), unique-local (`fc00::/7`), multicast (`ff00::/8`), and localhost forms are all rejected. On the runner path the feed hostname is additionally RESOLVED before any request (`resolveFeedHost`) and every resolved address must pass the same checks — and the connection is pinned: the connector (a core-`http`/`https` implementation, no new dependency) installs a connect-time DNS lookup hook (`pinnedHttp.ts`) that resolves ALL addresses, validates EVERY one against the same checks, and only hands Node addresses that passed — fail closed, no partial connections — so the destination cannot drift between validation and connect (the DNS-rebinding window of a fetch-based transport is closed). One-shot agent per fetch: no pooled socket is ever reused under an earlier validation. SNI and TLS hostname validation use the ORIGINAL hostname (an IP-literal host carries no SNI), and Node's default certificate verification is preserved. Redirects are NOT followed, so a feed cannot be laundered into an internal address; responses are capped by declared content-length plus an incremental read cap (`MAX_FEED_BYTES`) on the DECOMPRESSED stream (gzip/deflate/brotli are decoded with the cap applied after decompression, so a small hostile payload cannot expand past the cap), with a hard fetch timeout covering resolution, connect, headers, and body; every early reject destroys the request and aborts the timer, so a rejected fetch never leaves a connection draining. Parsing is excerpt-level only — titles, links, and summary/description text; there is no full-page fetching anywhere in the domain. The parser is deliberately tolerant (real feeds are messy) but bounded: entries without an http(s) URL and a non-empty title are skipped; item URLs are canonicalized and length-capped (`MAX_ITEM_URL_CHARS`) at parse time, so a hostile item is isolated there instead of failing the persistence transaction for the whole batch; titles and excerpts are stripped of control characters (including NUL, which PostgreSQL text cannot store); entities are decoded, markup is stripped (script/style blocks removed, never evaluated), and excerpt length is capped at parse time.
- **Reaction pipeline (`runner.ts`).** Each attempt claims eligible items under a claim lease (`article_reaction.state = 'generating'` with an expiry) so replicas never double-generate, runs the bounded generation → review flow with the configured model, and finalizes each reaction into a terminal state: `accepted` (reaction text kept), `rejected` (review verdict), or `failed` (unusable output or runtime error). Attempts are durable and bounded (`max_reaction_attempts`) — the cap is enforced atomically at claim time (not only at selection), and a row whose budget is exhausted while stalled in `generating` (a crashed worker's lease) is settled into an honest terminal failure on the next attempt instead of sitting as a zombie lease. Candidates come only from currently enabled feeds (an item whose feed was disabled after it was fetched never reacts), a per-run budget caps generation attempts (`max_generations_per_run`), a hard cap bounds feeds attempted per run (`MAX_FEEDS_PER_RUN`) with the runtime rotating the starting position across runs so no enabled feed is starved, and items older than the configured age limit are never reacted to. Accepted reactions become real `memory_fact` rows attributed to the assistant subject — `source_type = 'article'`, the fact's turn id null, and `article_reaction_id` pointing at the reaction — written in the SAME transaction that marks the reaction accepted, so a fact never exists without its provenance (and a crash between the two writes is impossible).
- **Memory-model extension (migration `0007_article_work`).** `memory_fact.turn_id` becomes nullable and exactly one source is enforced by CHECK constraints (a conversation turn XOR an article reaction, with `source_type` matching the link). Turn-sourced facts keep their existing columns and behavior unchanged. Turn-based consolidation excludes article facts (they carry no turn), and article-sourced facts surface through recall with their source attribution rather than a turn reference.
- **Idempotency.** Fetched items persist once per URL (`article_item` unique); a re-fetch refreshes provenance without duplicating items. A reaction is one row per item with a stable synthetic fact key derived from the reaction id (`article:<reaction-id>`), so the accepted-fact write is idempotent by key and an accepted reaction can never be regenerated.
- **Tracing.** Attempts record metadata-only `memory_operation` rows with kind `article_ingestion` (counts, ids, bounded categories — never prompt or response text), following the established memory tracing pattern.
- **Interest consolidation (`observation.ts`).** Every ingestion attempt ends with a fail-soft, turn-free consolidation phase over the unconsolidated accepted article facts (assistant-subject preference facts not yet referenced by any observation or omission evidence, bounded per run and trimmed to the rendered source cap, so a batch of long reactions cannot exceed the bound and fail repeatedly). The provisioned consolidation prompt only groups claims and cites fact ids; the subject and kind are code-owned (assistant, preference), and evidence breadth is distinct independent reactions — never turns, so the observation honestly records zero turn evidence. Accepted candidates become ordinary `memory_observation` artifacts of a `memory_run` with `max_turns = 0`, promoted by the existing engine with unchanged fencing, idempotency, and verification; a run with no accepted candidate is terminally failed (`no_accepted_article_interest_candidates`) so promotion never retries it while the facts stay pending for a later attempt. The phase is single-flight under a durable claim (`article_observation_claim`, migration `0009`): a concurrent worker skips instead of duplicating the provider call and artifacts (`consolidation_in_progress_elsewhere`), a crashed worker's expired lease is taken over by the next attempt, and every artifact write is fenced by the exact lease it was claimed under. A missing behavioral boundary, assistant subject, or consolidation prompt skips the phase; every failure is logged with a fixed category and never fails the ingestion attempt.
- **Per-turn share decision (`share.ts`).** One optional `choice` decision question per turn — a second decision on the same attempt — offers the cooldown-eligible accepted reactions (newest first, each described by its article) plus a permanent typed `none` option. The decision selects context inclusion for this turn only and never asserts that a memory was or will be shared; mentioning is never a requirement. Candidates are bounded (`decision_max_candidates`), deduplicated against the facts the lexical recall chunk already surfaced, and cooldown-filtered from the newest `article_share.included_at`. A selected candidate becomes its own synthetic `article` system chunk — background context with provenance, never an instruction to share and never a claim that anything was shared — and the inclusion is recorded once per (reaction, turn), idempotently under turn retries. An unusable answer fails the turn without a silent fallback; an unprovisioned, incomplete, or disabled deployment asks no question.
- **Retrieval surface (`retrieval.ts`).** `GET /v1/articles/memories` on the private API serves accepted article memories newest-first with a caller-configurable integer limit (default 20, hard-bounded; out-of-range or non-integer values are validation errors the API maps to `400`). Retrieval is source-filtered (article-sourced facts only) and deterministic; a server without the surface wired reports `503` rather than serving an empty imitation.

## Data model

Domain-owned migration `0001_conversation_work`:

- `conversation_turn` — id, status, attempt, lease owner/expiry, selected pattern id, decision diagnostics (jsonb, legacy), error, timestamps.
- `conversation_message` — id, identity-based `seq` thread position, role (`user`/`assistant`), content, nullable idempotency `client_key` (unique; a key is bound to exactly one content — reuse with different content is rejected as a conflict), nullable `turn_id` reference. At most one assistant reply per turn (partial unique index).
- `response_pattern` — id, enabled, `selection_description` (for the decider), `response_guidance` (for chat), presentation `position`.

Domain-owned migration `0002_conversation_tracing` (attempt tracing; relational, feature-specific — no generic JSONB payload, document facade, or EAV):

- `trace_attempt` — one row per attempt of a turn (initial claim or reclaim), created inside the claim/reclaim transaction; `claimed_at`, nullable `finished_at`/`outcome` (`published` | `failed` | `fenced` | `superseded` via a check constraint), the `snapshot_recorded_at` marker, and nullable typed temporal fields for timezone, instant, local civil date/time, season, and occasion selection/context. A reclaim marks the previous open attempt `superseded` atomically with the lease replacement. Unique per `(turn_id, attempt)`.
- `trace_attempt_context` — the exact ordered context the attempt saw, by `conversation_message` id reference, in position order.
- `trace_attempt_pattern` — the mutable response-pattern configuration as it stood at the snapshot: each pattern's full `selection_description`/`response_guidance` content and presentation position.
- `trace_attempt_decision` — the attempt's decision boundary: a `state` (`requested` before the provider call; `responded`, `failed`, or `invalid` after it), question id/type, request model, instructions as sent, the returned choice (nullable: absent when the selection was rejected or never resolved), nullable confidence, a `probabilities_present` marker that keeps a present-but-empty native probability distribution (zero child rows) distinguishable from an absent one (no distribution at all), the recorded selection outcome (`selected`/`rejected`) with its rejection reason, nullable response model/provider/id and usage columns, and nullable error kind/message/body for the `failed`/`invalid` states (the actual transport or contract error; error body only when the transport retained one, and never for `invalid`); absence of optional native values stays absent.
- `trace_attempt_decision_probability` — the optional per-option probability distribution the provider returned, one row per option (no rows means none was returned).
- `trace_attempt_chat` / `trace_attempt_chat_message` / `trace_attempt_chat_choice` — the chat boundary: request model/temperature/max_tokens and a `state` (`requested` before the provider call; `responded`, `failed`, or `invalid` after it), response id/model, usage, nullable error kind/message/body (the actual transport or contract error; error body only when the transport retained one), the exact ordered request messages (each linked to its `conversation_message` row; the synthetic guidance and memory system messages' source is null), each returned choice, and the reply content (null until the response succeeded). A `responded` row additionally carries `application_rejection` — the reason the application rejected an arrived response (e.g. no usable choices) — recorded separately from the transport outcome so the trace stays unambiguous about what arrived and whether the application accepted it.
- `trace_attempt_chat_message.chunk` (migration `0004_chat_identity`) — the assembly-chunk classification of each recorded message; null for rows recorded before the classification existed.
- `trace_attempt_chat.identity_revision` (migration `0004_chat_identity`) — the `chat_identity` revision the request carried; null for rows recorded before the column existed.

The legacy `conversation_turn.decision` JSONB column is preserved untouched for pre-tracing history and is no longer written by new work; the trace tables above are the new home for decision diagnostics. The report presents both, clearly marked.

Domain-owned migration `0004_chat_identity` (chat identity; runtime configuration like `response_pattern` — generic structural schema, provisioned per deployment, never seeded):

- `chat_identity` — the owner-authored identity/persona text sent as the leading system message of every chat request: one singleton row (`id = 'identity'`) with the content, an owner-managed `revision` counter recorded on each chat boundary trace, and `updated_at`; a CHECK constraint rejects empty content. Missing or empty identity is a fail-closed configuration error, never an invented persona.

Domain-owned migration `0005_message_timing` (original message timing for user messages; relational provenance — see [Message timing](#message-timing) and [`src/conversation/timing.md`](src/conversation/timing.md)):

- `conversation_message` gains `client_sent_at` (nullable — the raw client-reported send time as received, kept even when it was not trusted; null when absent or unparseable), `server_received_at` (NOT NULL — the server clock reading at ingest, kept honest and identical to `effective_at` on every fallback), `effective_at` (the trusted working time chosen at ingest — the client time when valid and ordered, otherwise the actual recorded receipt, never clamped or synthesized), `time_source` (`client`/`server`), and `client_time_status` (`absent`/`valid`/`future_skew`/`out_of_order`/`invalid`) — the last four NOT NULL after legacy rows are backfilled from their own recorded history: `server_received_at` = `effective_at` = `created_at` (the row's server insert instant), status `absent`, and no original client time invented (no client time was recorded before this migration). A partial index over user rows supports the ingest path's acceptance/order-bound lookup (the maximum effective time over user rows — the monotonically tracked client-candidate validation bound and the engagement last-activity clock).
- The engagement domain reads `effective_at` by foreign-key-adjacent query (same cross-domain read shape memory uses); the timing columns themselves remain owned by the conversation domain.

Domain-owned migration `0006_conversation_thread_order`:

- `conversation_turn.thread_order` and `conversation_message.thread_order` share a database sequence for the ordering boundary of a claimed turn or standalone assistant publication. Messages in a turn retain their own `seq` order; standalone assistant notices use their publication ordinal. This keeps queued user messages from pulling a later-claimed turn ahead of an intervening notice in later-turn context. The migration backfills legacy turn order by first user-message `seq`; legacy standalone assistant messages are placed after the turn with the greatest first-user `seq` below the notice's own `seq`, or before all turns if none precedes it, because earlier schemas did not persist a claim/publication ordinal.

Migration ids are feature-owned labels, not a global sequence: the composition array (`main.ts`) applies the conversation domain's migrations (0001, 0002, 0004, 0005, 0006) before the memory domain's (0003) and the engagement domain's (0006), because the memory and engagement tables hold foreign keys into conversation tables. The article domain's migrations (0007, 0008, 0009) apply after conversation and memory, because `article_share` references conversation turns and the article migrations extend memory tables; the routine schema, chat-chunk widening, announcement outbox, and period-identity upgrade (0012, 0013, 0014, 0015) apply after the conversation tracing schema. The migration runner is forward-only, and migration compatibility is per-migration, not blanket: most changes are additive or only widen constraints, so a previous binary that encounters a recorded-but-unrecognized migration id leaves it untouched and keeps working for unaffected tables — but 0008 is the exception: it relaxes `trace_attempt_decision` from attempt-wide uniqueness to (attempt, question), and the previous binary's decision writes use `ON CONFLICT (attempt_id)`, which fails (`42P10`) on the migrated schema. A previous binary therefore cannot record conversation decisions on a 0008-migrated database, so a mixed-version deployment that serves conversation turns is not supported once 0008 is applied. There is no downgrade path in any case: the schema stays at the highest applied migration. Migrations `0016_authoritative_temporal_context` and `0017_trace_attempt_temporal_context` create the private worker-wide timezone/season/birthday settings and typed chat-attempt temporal trace fields. Migration 0016 copies a timezone only when the existing memory, relationship, and routine settings agree; conflicting values abort that migration transaction without changing the legacy timezone columns. Those existing columns remain for historical/config compatibility but are no longer read by runtime consumers. A timezone change is an operator-controlled restart cutover, not an automatic migration or deployment action.

Domain-owned migration `0003_memory_work` (the memory pipeline; relational, feature-owned — no JSONB payload, document facade, or EAV for memory content; `text[]` appears only as topic arrays):

- `memory_subject` / `memory_prompt` / `memory_behavior` — runtime configuration: subjects (with per-subject flags such as profile participation and the per-subject v1 evidence-attribution rule), versioned prompt texts for every memory LLM task, and the distinct memory behavioral-day start hour. The timezone comes from the worker-wide temporal settings row. Personal behavior values are provisioned per deployment, never seeded by migrations; loading is fail-closed.
- `memory_fact` / `memory_fact_source_message` — durable production facts (typed, keyed, content-hashed, with observation-worthiness and retraction status) and their per-message source links.
- `memory_turn_extraction` / `memory_turn_extraction_item` — the per-turn extraction cache: which turn was extracted with which prompt version and which facts/items it produced, making ingest re-runs no-ops.
- `memory_run` / `memory_run_turn` — consolidation run records and the turns each run covered.
- `memory_observation` / `memory_observation_evidence` — consolidated observations (claim, condition, consequence, type, status, evidence strength) and their resolved fact-evidence links with role and position.
- `memory_observation_omission` / `memory_observation_omission_evidence` — explicitly reported things the consolidation model could not turn into an observation, with their own evidence links.
- `memory_canonical_observation` — the promoted recall surface: one row per promoted observation identity, with content hash, first/last-seen evidence, a tsvector over claim/condition/consequence, and a partial GIN index for active rows.
- `memory_observation_history` — append-only status/reason history for observations (automatic transitions and manual reason-coded retractions).
- `memory_promotion` / `memory_promotion_item` — promotion runs: the plan hash, safeguards outcome, and per-item results; idempotent per observation.
- `memory_temporal_summary` / `memory_temporal_summary_message` — behavioral-period summaries keyed by subject, period type, and period start, with source-message links.
- `memory_profile_summary` — profile-v1 subject sheets distilled from temporal day summaries, fingerprint-gated.
- `memory_observation_profile` / `memory_observation_profile_claim` — profile-v2 observation documents per subject with their input fingerprint and claim rows.
- `memory_ingest_state` — the singleton ingest watermark (last processed turn id, last activity) that makes ingest restartable.
- `memory_operation` — metadata-only memory operation traces: kind, outcome, referenced ids, timing. Never prompt or completion content.

Domain-owned migration `0006_engagement_assessment` (the engagement domain; relational, feature-owned — no JSONB payload, document facade, or EAV):

- `engagement_bands` — the band-cutoff runtime configuration: one singleton row with the THREE strictly increasing cutoffs in milliseconds (`lull_ms` < `idle_ms` < `gone_ms`) delimiting the four half-open bands. Provisioned per deployment like `memory_behavior` and `chat_identity`, never seeded by migrations and never a code default; unprovisioned deployments run engagement as a safe no-op (see [Engagement](#engagement)).
- `engagement_message_assessment` — one row per NEW user message (primary key = `conversation_message` reference): the assessed `state`, the previous user message's recorded `previous_state` (null for the first), the measured `silence_ms` (null for the first), the `retained_lull` marker, the message's `message_effective_at` provenance, the band cutoffs the assessment was computed with (a per-row snapshot, so later configuration changes never rewrite history), and `assessed_at`. Written exactly once, inside the ingest transaction; never written for assistant messages or idempotent replays.

Domain-owned migration `0007_article_work` (the article domain; relational, feature-owned — no JSONB payload, document facade, or EAV):

- `article_feed` / `article_behavior` / `article_prompt` — runtime configuration: the feed list (with enabled flag and ordering position), the single-row ingestion policy (enable switch, model, generation/attempt budgets, age limit, reaction and excerpt character caps, candidate and cooldown policy), and the versioned persona prompts for the two article LLM tasks. Provisioned per deployment like `memory_behavior` and `chat_identity`, never seeded by migrations; loading is fail-closed (see [Articles](#articles)).
- `article_item` — one row per fetched feed item, keyed UNIQUE by URL: the bounded excerpt the reaction was generated from (never full-page content), its feed, title, publish date, and fetch stamp.
- `article_reaction` — one reaction per item with a terminal-state machine (`generating` under a claim lease → `accepted` | `rejected` | `failed`), a durable attempt count for bounded retries, the generated reaction text, the model and prompt versions that produced it, lease fencing for replicas, the review verdict's bounded reason, and the back-reference to the memory fact key created on acceptance (CHECK-constrained so exactly the accepted state carries a reaction and a fact key).
- `article_share` — prompt-inclusion records: one row per time an accepted reaction's memory was included in a chat prompt (with the including turn, nullable for API shares). This records INCLUSION, not a claim that the memory was actually shared; the share cooldown is computed from the newest inclusion.
- `memory_fact` gains the article source model: `turn_id` becomes nullable and every fact has exactly one source — a conversation turn XOR an accepted article reaction — with `source_type` (`conversation`/`article`) constrained to match the link, plus a partial index over article-sourced rows.
- Trace kinds `article_ingestion` and `article_memory_share` join the `memory_operation` kind CHECK, and the chat trace's chunk CHECK gains the `article` synthetic-system-chunk classification — applied by migration `0008_article_share_and_evidence` alongside the share feature's other trace-shape changes, not by the additive `0007_article_work`.

Domain-owned migration `0009_article_observation_claim` (the article domain):

- `article_observation_claim` — the durable single-flight claim for the turn-free interest-consolidation phase: one row (`id = 'consolidation'`) with an owner token and a lease expiry. A concurrent worker skips instead of duplicating the provider call and artifacts; an expired lease is how a crashed worker's claim is recovered; artifact writes are fenced by the exact lease they were claimed under (see [Articles](#articles)).

Domain-owned migrations `0012_routine_schedule`, `0013_routine_chat_chunk`, `0014_routine_announcement`, and `0015_routine_announcement_period_id` (the routine domain):

- `routine_settings` / `routine_transition` — the departure context and recurring state transitions; schedule timezone comes from `companion_time_settings`.
- `routine_applied_transition` / `routine_applied_state` — durable occurrence history and current applied state, separate from the schedule projection.
- The `trace_attempt_chat_message.chunk` constraint gains `routine` so routine context remains classified in the exact chat trace.
- `routine_announcement` — typed pending/published/cancelled/ended events with UUID period identity and a linked assistant `conversation_message`, providing publication correlation and restart recovery without creating a user-turn attempt. Migration `0015` replaces the transition/date primary key; binaries that only understand the `0014` key/status contract must not be mixed with a database after `0015` is applied.

Domain-owned migrations `0016_authoritative_temporal_context` and `0017_trace_attempt_temporal_context`:

- `companion_time_settings` — one private singleton carrying the authoritative IANA timezone plus optional meteorological hemisphere override and birthday month/day. Migrations contain no personal selections. Existing timezone values are consolidated only if all provisioned legacy settings agree; a conflict aborts the migration rather than choosing a zone.
- `trace_attempt` gains typed per-chat-attempt local date/time, timezone, season, and selected occasion context, aligned with the exact synthetic temporal message saved in the chat boundary.

The schema is relational PostgreSQL only. No identity-provider subjects, user ids, or tenant identifiers appear in any table. Traced content is recorded as returned — there is no platform-wide filtering or expiration of recorded conversation content.

Personal behavior configuration (subjects, persona prompts) is not environment content — it lives in `memory_subject`/`memory_prompt` (see [Memory](#memory)).

The numeric defaults are provisional operating points for this slice, not settled policy; all are configurable. Message input bounds (20,000-character content, 64 KiB bodies, client-key shape) are contract constants in `api/server.ts`, not configuration. The engagement band cutoffs are deliberately not environment variables and have no code default: they are provisioned per deployment in the `engagement_bands` table (see [Engagement](#engagement)), and an unprovisioned `engagement_bands` row disables engagement regardless of any environment setting.

## Running

```sh
pnpm --filter @companion/worker start
```

Startup validates configuration, connects to PostgreSQL, applies domain migrations (idempotent, advisory-locked), starts the private HTTP API (which requires its service credential), runs the engine loop until `SIGINT`/`SIGTERM`, starts the in-process article-ingestion scheduler on every run (fail-closed: an unprovisioned article domain is the `ingestion not configured` no-op, and its provisioned configuration — not the memory feature flag — decides whether it does work), and — when memory is enabled — starts the in-process memory scheduler (ingest reconciliation, temporal sweeps, scheduled profiles) with the same graceful-shutdown ordering: the engine stops claiming, queued work drains, the HTTP listener drains in-flight requests, and only then is the connection pool closed. Missing configuration exits with a named-variable error; missing memory runtime configuration (subject/prompt rows) fails closed the same way when memory is enabled.

The migration-only command applies the same complete, ordered worker migration composition and exits without starting listeners, schedulers, or the engine. It requires `WORKER_DATABASE_URL` and is intended for controlled schema maintenance:

```sh
pnpm --filter @companion/worker migrate
```

Like the other database-backed suites it is skipped without `WORKER_TEST_DATABASE_URL` and truncates its tables — disposable databases only.
- Attempt tracing is covered by the same integration suites: decision-then-chat failure leaves the full decision boundary (including the recorded selection) and a `failed` chat row carrying the actual error, with a `failed` attempt outcome; a decision transport failure records the request before the provider call and a `failed` decision outcome carrying the real error (with no invented response data); a malformed decision body records an `invalid` decision outcome with the validation error and no persisted offending value; the chat request is recorded in `requested` state before the provider call and transitions to `responded`, `failed`, or `invalid` after it; a provider response with no choices fails the chat contract and is traced as `invalid` with the real validation error (no invented reply content); an application rejection on an arrived response is persisted separately from the transport outcome on a `responded` row; each attempt's pattern snapshot is preserved when the mutable pattern configuration changes between attempts; a rejected selection still leaves the complete decision response behind (the boundary is written before the selection step); a lease reclaim marks the previous attempt `superseded` atomically with the lease replacement, and the stale worker's late self-report is a no-op; a misaligned trace write fails its own transaction leaving no partial rows; a legacy pre-tracing turn and its decision JSONB survive the tracing migration untouched; and the assembled turn trace report (and the CLI rendering it) carries every recorded boundary — publication is rendered only from the turn's actual status, and the CLI's render functions are covered by hermetic unit tests for all new states (including decision failure/invalid states and application rejections).
- The chat/decision transport level is verified with fakes only; no live OpenRouter call has tested the typed decision flow. The memory pipeline's prompts and LLM adapter were additionally exercised against the live OpenRouter API in a one-off local validation run (synthetic content, agent-owned key, disposable database, uncommitted script): fact extraction, consolidation, automatic promotion, canonical recall, temporal leaf/day/month generation, profile v1 and v2, the fingerprint gate, and the assembled chat memory context all produced accepted output, with one real model output correctly rejected by the temporal validation gate (fail-closed, nothing stored). The committed suites remain fake-only.

## Open questions

- Retry policy for failed turns (currently terminal: `failed` turns are not retried) and whether transient errors should re-queue.
- Decision fallback/calibration: thresholds, top-N ranking, behavior for unusable or low-confidence answers.
- Trace retention: what is kept in the `trace_attempt*` tables and for how long (currently no platform-wide filtering or expiration), and the legacy `conversation_turn.decision` JSONB column's eventual disposition.
- Whether response patterns and the conversation schema should move to a shared domain home as more of the thread surface needs the same tables.
- Lease/reclaim refinements: persisted worker identity for immediate self-reclaim after restart, bounded reclaim attempts.
- Queue technology and context-window policy remain open; this slice uses PostgreSQL-backed leasing and a configurable fixed history limit.
- TLS between the BFF and the worker's private listener (currently plain HTTP inside the cluster boundary, guarded by the bearer token) if that boundary ever leaves the cluster network.
- Memory tooling: the `memory-cli` covers canonical observation inspection, the token-confirmed policy review (including policy retraction), a read-only automation report, and the recall-ranking evaluation (`recall-eval`: seeds a generic synthetic corpus into a disposable test database, runs every corpus query through the real recall pipeline, reports recall@k, precision@k, MRR, and temporal-window violations against env-tunable thresholds, and removes its own rows afterwards). The evaluation enforces an empty-domain precondition — it refuses any target that already holds conversation, fact, canonical, or subject rows, so in-use or provisioned databases always refuse — and refuses when `WORKER_TEST_DATABASE_URL` equals `WORKER_DATABASE_URL`; it echoes the connected database and role (never the connection string). This is an emptiness precondition, not proof of disposability: the tool cannot distinguish an unused application database from a disposable one, and choosing the target remains the operator's responsibility. The evaluation covers recall ranking only; batch evaluation tooling for extraction and consolidation quality is not implemented. The general recall surface is served by the worker's private API (`POST /v1/memory/recall`, above). Remaining unimplemented gaps, not scope decisions: profile-serve generation gating and model binding for the v1 sheet pipeline (only the v2 profile and temporal pipelines carry the serve-time generation-settings checks), the temporal summary's `with_turn_log` read-back, batch evaluation for extraction and consolidation, and backfill/import tooling for pre-existing history (deliberately not implemented). A decision on where memory ops tooling should live long-term is still open. Prompt content itself is per-deployment configuration, so its iteration workflow is a deployment concern.
- Engagement consumers: engagement is recorded and served in this slice, but no other domain reads it yet — whether and how it should join the response-pattern decision, chat guidance, or any user-visible surface is an open product decision. A browser-facing engagement route (BFF `/api/engagement` and UI) is likewise not implemented.
