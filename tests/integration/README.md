# Integration tests

## Responsibilities

Checks of interactions between domain components and their infrastructure boundaries: relational persistence, durable grouped work, typed provider adapters, and recovery/error paths.

[`memory-embedding-service.test.mjs`](memory-embedding-service.test.mjs) is an explicitly invoked, non-database integration check for the configured real embedding service. It verifies readiness, model/revision/dimension metadata, and query/document batches through the worker's production client using harmless synthetic strings. It performs no database writes and does not call the chat/decision provider. Run it only with `WORKER_MEMORY_EMBEDDING_BASE_URL` populated from the approved local infrastructure configuration; the endpoint is intentionally not recorded in this repository. The normal unit suite remains hermetic and uses injected embedding fakes.

```sh
node --test tests/integration/memory-embedding-service.test.mjs
```

## Boundaries and safe targets

Several database-backed suites use `TRUNCATE`, synthetic runtime configuration, fault injection, or destructive migration fixtures. They are explicit isolated-test tools, not routine shipping gates. Set `WORKER_TEST_DATABASE_URL` only to a positively verified disposable database dedicated to the current run; never point it at any maintained application database, including non-production. If a suite has no safe target, Node reports it as skipped; do not substitute the maintained database. Use run-owned containers/schemas and cleanup that verifies exact ownership before removal. Migration-upgrade fixtures may create and drop unique schemas only after confirming their ownership; they must not drop/recreate `public` or remove pre-existing extensions. pgvector must already be available in the disposable target where semantic tests require it; migrations do not install the extension.

The delivery workflow validates database-changing code with focused disposable persistence checks where relevant, then applies only the candidate's ordinary forward migrations to non-production. It does not reset the maintained database, replace provisioned identity/personality/settings/modules, stop its consumers for tests, or capture/restore its configuration. Deployed validation uses normal application flows and uniquely attributable synthetic scenario data; its existing configuration must remain invariant. The routine deployed smoke intentionally retains its conversation, trace, and normal learned effects as non-production history. Do not rewind cursors/counters or delete baseline, shared, canonical, or otherwise ambiguous state. Legacy cleanup is explicit-only for selected historical markers and is never a routine gate. If configuration invariance or candidate isolation cannot be proved, stop before the affected operation.

The disposable local PostgreSQL used by Playwright is a separate run-owned fixture. Configure each local stack, tooling, or deployed-smoke run with a new unique `E2E_RUNS_DIR` outside the historical `tests/e2e/.runs` directory. Do not invoke unrestricted reconciliation or cleanup against the historical directory.

## Scope

The current suites use Node's built-in test runner like the unit suite. Vitest remains a possible future direction, not an approved or installed dependency; do not introduce a second runner casually.

## Open questions

The runner-free deploy trigger/controller remains unresolved. Database integration suites that mutate persisted state remain opt-in isolated tools; no application-database exception is part of the release workflow.
